# FrameFlow Design Notes (as built)

## Overview

**Threads.** Three per run. The *source thread* (`SourceRunner`) asks the `ISource` for frame k,
waits until `t0 + k / fps`, stamps the scheduled capture time, lateness and backpressure (D13,
D38) and pushes. The *worker thread* (`Worker`) pops, may drop a stale frame (adaptive, D47),
runs the processor and the synthetic cost, hands the frame to the sink and feeds the latency
back to the policy. The *main thread* parses options, checks everything that can fail before
any thread starts (input file, output folder, display, root), waits for the end in
`Pipeline::run()` (ticking once per second for memory sampling and `--progress`, D52, D56), then
writes the result files. A fourth, the signal watcher, exists for the whole command (D33).

**Ownership.** A frame is a `std::unique_ptr<Frame>` owned by exactly one place at a time:
source -> queue -> worker -> sink -> freed, or -> drop callback -> freed. Its metadata is copied
into the preallocated `MetricsStore` slot of its id exactly once (delivered, dropped, or in
flight at the end).

**Synchronisation.** `BoundedQueue` has one mutex and two condition variables, always waited on
with a predicate. Policies decide under the queue lock and never call back into the queue; the
adaptive policy's own mutex is always taken after the queue's (D44). Pipeline state (source
done, stop requested, error) has its own mutex and condition variable. The only atomics are the
stop flag, the live counters (D52) and the signal count. TSan runs the full suite and the
stress tests; OpenCV's own thread pool is off so that every thread is visible to it (D50).

**Invariants checked on every integration run** (`tests/integration/invariants.hpp`): BR-01
produced = delivered + dropped + in flight, with ids 0..produced-1 each recorded once; BR-02 a
dropped frame is never delivered; BR-03 delivery order follows ids; BR-04 the timestamps of a
delivered frame never go backwards.

**Ends.** Duration, frame count, end of input, stop request (Ctrl+C, q in the preview) and a
thread error all go through one shutdown routine (D17); frames still queued are in flight. The
second Ctrl+C exits 130 at once.

**Modules.**

| Folder | Contents |
| --- | --- |
| `include/frameflow`, `src` | `Pipeline`, `BoundedQueue`, `SourceRunner`, `Worker`, `Clock`, `Frame`, config, CLI, run command |
| `policy/` | `OverloadPolicy`, blocking, drop-oldest, drop-newest, adaptive (+ `LatencyWindow`), factory |
| `source/`, `processor/`, `sink/` | synthetic and video sources; none/grayscale/blur/canny + cost model; null and preview sinks |
| `metrics/` | `MetricsStore`, `Stats`, `RunReport`, warnings, CSV and JSON writers |
| `bench/` | experiment files and `BenchRunner` |
| `platform/` | the only OS-specific code: signals, `/proc`, display/terminal, privileges, output folder (RR-12) |
| `ui/` | console summary, progress line |

**Known limitations** (each with its decision): adaptive cannot exceed the throughput limit and
learns cost spikes only through an EWMA (D45, D47); the preview delays processing (D51);
processing is single-threaded by design (D50); a container whose frame count is too high reports
a decode error at its real end (D49); `--out` symlink rules follow paths, not mounts (D31).

| D33 | Signal handling | No async signal handler. `SignalWatcher` blocks SIGINT/SIGTERM in the main thread before any other thread starts (so all threads inherit the block) and one watcher thread takes them with `sigtimedwait` (50 ms timeout, so its destructor returns quickly). Second signal (any mix of SIGINT/SIGTERM): `error: forced exit, results may be incomplete` and `_exit(130)`. Messages use raw `write(2)` on the watcher thread. The watcher lives until the result files are written. | D35 | Console summary | S4 is printed to stdout after the result files are written; warnings follow on stderr as `frameflow: warning: <message>` (ER-07 wins over UIUX S4's "between the result block and the file line": they appear there in a terminal because stdout is flushed first), then the `Files` line or the error. | D36 | Output FPS | Fix of P2.4: `output_fps` = frames whose `t_out` is inside `[t0 + warmup, t_end)` / `window_s`, a delivery rate (SPEC 10 "delivered / measured duration"). | D37 | Phase 2 integration tests | Overload tests use 2 s runs at 50 fps with a queue of 4: at 2.0x (40 ms cost) dropping policies must drop 40-60% after warm-up; at 10x (EC-03, 200 ms) 80-97%. Blocking is checked with a hard lower bound instead of a timing: frame k cannot finish before `t0 + (k+1) x cost` and was scheduled at `t0 + k x interval`, so `latency_k >= (k+1) x cost - k x interval` (linear growth). "Bounded" for dropping is relative: max latency below half of blocking's, and the last third's mean latency not above 1.5x the first third's. The SR-04 stress run is 3 x 20 s (one per policy, BR-08) at 2.0x with a queue of 1, label `stress`. PR-10 is a `timing` test (release only, D9) on a synthetic 1800-frame report. | D38 | Lateness vs backpressure | Fix of the D35 lateness warning, which fired on about 91% of frames for blocking at 1.5x. Lateness is measured before the push, but under blocking the source spends time inside the push of frame k-1 while the release times of frames k, k+1, ... pass, so *later* frames are late (excluding frames whose own push blocked would not help). `FrameMeta::backpressure` is the share of `source_lateness` caused by earlier push waits: the source adds each push's duration to a pending total, and at every release the share is `min(pending, lateness)`, after which pending is capped to that share, so waiting the source has caught up on is forgotten and cannot hide later slowness. The ER-07 warning uses `own_lateness() = source_lateness - backpressure`; the message is unchanged because it now only fires when the source itself is slow. `frames.csv` `lateness_us` stays the total (DR-01 fixes the columns); `backpressure` is kept in memory only. | SRS ER-07, EC-12, FR-SRC-07, DR-01; D35 |
| D39 | Bursty schedule | A frame costs `--spike-ms` when its processing *starts* inside a spike. Spikes start at `t0 + offset + n x every` and last `len`; `offset` = (two `std::mt19937` outputs, seeded with the 64-bit seed folded to 32 bits, combined to 64 bits) mod `every` in clock ticks. Distributions are avoided because their output differs between standard libraries; the mt19937 sequence is fixed by the standard. `--spike-len` / `--spike-every` take `<n>s`, `<n>ms` or a bare number of seconds (SPEC 13 writes `1s`, `5s`), each in (0, 3600] s. The spike flags are rejected unless `--cost-mode=bursty` (like VR-08's "only with adaptive"). | SRS FR-PROC-03, FR-PROC-04, VR-06; D5 |
| D40 | Config file schema | `run --config` and bench files share one schema, the UIUX 8.3 template's keys: `source: {type, resolution, fps, input}`, `processor: {type}`, `duration_s`, `frames`, `warmup_s`, `seed`, `cost_ms`, `cost_mode`, `cost_wait`, `spike_ms`, `spike_len`, `spike_every`, `queue`, `policy`. Each value is kept as its YAML text and checked by the same `validate()` as the flags (VR-18), so error lines name the matching flag (e.g. `--queue 0`). Structural problems (unknown key with closest match, non-scalar value, syntax) are `file:line:col:` errors, exit 2. `processor.type` must be `synthetic` until Phase 5 adds processors. `experiment`, `repeats`, `matrix` are refused by `run --config`. Files over 1 MB are refused before parsing; after parsing, the scalar text is counted with every alias use expanded, stopping at 1 MB (SR-07). | SRS VR-18, SR-07, FR-CLI-01, EC-19; UIUX 8.3 |
| D41 | Matrix expansion | `matrix` maps run key paths (e.g. `cost_ms`, `policy`, `source.fps`) to non-empty lists without duplicates. The cartesian product is taken in file order with the last key varying fastest. A configuration's folder name is `<last part of key>-<value>` joined by `_` (e.g. `cost_ms-40_policy-blocking`; characters other than letters, digits, `.` and `-` become `-`); an empty matrix gives one configuration named `default`. Every configuration is validated like a run before anything starts; at most 1000 configurations. | SRS DR-05; UIUX 8.3 |
| D42 | Bench layout and flow | `frameflow bench --config <file>` takes only `--repeats`, `--out` (parent folder, default `results`), `--overwrite`, `--allow-any-out`, `--allow-root`; run settings come from the file. Layout: `<out>/<experiment>/<config>/rep_<n>/` (n from 1) with the four run files, and `<out>/<experiment>/experiment.json`, rewritten after every run via a temp file and `rename` so it is always current (EC-20). Runs are sequential; a failed run is recorded and the bench continues (exit 1 at the end if any failed). Ctrl+C stops the current run gracefully (status `interrupted`, its partial folder kept but listed under `missing`) and skips the rest (status `missing`), then prints the missing list; exit 0. One progress line per run (the outcome is appended to the line when the run ends); the final table shows medians over *completed* repeats, with p95 min-max (BR-11; the mean of the two middle values for an even count). | SRS FR-CLI-02, DR-05, BR-11, EC-20; UIUX S5 |
| D43 | analyze.py | Input: an experiment folder, a folder of them, a run folder, or a folder of runs. `experiment.json` decides which repetitions count: only `completed` ones, and of those only `valid` ones go into the tables (`invalid_runs` is reported). Tables per experiment: `summary.csv` (all metrics, median/min/max) and `summary.md` (median (min–max)); `null` metrics stay empty, never 0. Charts per run (`latency_over_time.png`, `depth_over_time.png`, FR-ANA-01) and per experiment: configurations that differ only in `policy` share a chart (one line per policy, rep 1 of each, legend order and Okabe-Ito styles from UIUX 6.3/12.2, warm-up shaded, footer with CPU and kernel), named `..._<other params>.png` when the matrix has other keys. Errors exit 1 naming the file, the column and, for bad numbers, the line (ER-09); both JSON files must have `schema_version` 1. `--out DIR` also copies the experiment-level files to `DIR/<experiment>/` (for `docs/images`). Tests write their fixtures in `tmp_path`; one test runs the real binary (ctest `AnalyzePytest`, skipped under TSan). | SRS FR-ANA-01..03, ER-09, BR-11; UIUX S7, 6.3, 9.1, 9.4 |
| D44 | Adaptive policy interface | `OverloadPolicy` gains `is_stale(meta)` (asked per queued frame, queue lock held), `should_drop_on_pop(meta, now)`, `on_delivered(latency, now)` (SPEC 9.2 sketch plus `now`, so a state change has a time without the policy reading the clock again) and `state_changes()`. New `PushDecision::DropStale`: the queue removes every frame `is_stale` accepts (reason `stale`, queue order), then, if still full, the head (reason `oldest`, FR-POL-08 "drop the oldest"), then appends. SHEDDING returns `DropStale` on *every* push, full or not. Age = `now - t_cap`; stale = age > T (strict); enter = L > T, exit = L < T_low (strict, so L exactly at either threshold changes nothing). L is updated only by delivered frames; the incoming frame is never checked on push (it was just captured). The worker stamps `t_pop`, asks `should_drop_on_pop`, and a dropped frame gets `t_drop = t_pop` and no processing stamps. AdaptivePolicy guards state, window and change log with one mutex; lock order is always queue -> policy. | SPEC 8.4, 9.2; SRS FR-POL-05..09, BR-07, EC-13, EC-14 |
| D45 | Adaptive options and outputs | `--target-ms` (1-60000, default 100), `--exit-ratio` (0 < x < 1, default 0.7), `--window` (5-1000, default 30) are all rejected unless `--policy=adaptive` (VR-08's rule applied to all three); YAML `adaptive: {target_ms, exit_ratio, window}`. In bench files the file-level `adaptive:` section is applied only to configurations whose policy is adaptive, so one file can compare all four policies; adaptive keys in the matrix are kept, so pairing them with a fixed policy is an error. Outputs for adaptive only (null/omitted otherwise): `summary.json` config `target_ms`/`exit_ratio`/`window`, metrics `state_changes` (whole run, like frame counts) and `shedding_pct` (share of the measurement window in SHEDDING); `events.csv` rows `state_change` with detail `NORMAL->SHEDDING L_ms=…`; S2 `policy adaptive (target 100 ms, exit 70 ms, window 30)`; S4 `Adaptive` row. | D46 | Bursty and adaptive analysis | `summary.json` config gains `spike_offset_s` (first spike, D39), so analysis rebuilds spikes as `[offset + n x every, + len)` without re-implementing mt19937. Recovery time (SPEC 10) per spike that starts after warm-up and ends before the last capture: from spike end to the `t_out` of the first delivered frame with latency below T; 0 if the last frame delivered by the spike end was already below T; a spike that never recovers is left out of the mean. T is the run's `target_ms` (adaptive) or `analyze.py --target-ms` (default 100, the E3 adaptive target) for fixed policies, so all policies are judged against the same line. | D47 | Predicted delivery age | Fixes the D45 overshoot. A frame is stale when `(now - t_cap) + est_cost > T` (strict), both on pop (worker) and in shed-on-push (`is_stale`). `est_cost` is one EWMA of processing times (`t_proc_end - t_proc_start`), alpha 0.2, starting at 0, updated in `on_delivered`, which now also receives the processing time. It is kept in nanoseconds as a double under the policy mutex; `is_stale` now takes that mutex too (queue -> policy order unchanged). The EWMA is updated in NORMAL as well, so it is ready when SHEDDING starts; NORMAL still never drops (BR-07). Measured on the same 1.5x smoke run (12 s, 30 fps, 50 ms cost, T = 100 ms, debug build, two runs): p95 86.6 ms and max 86.7 ms, below T, with 33% stale drops (unchanged: throughput-bound) and output 20.0 fps. Limit: the prediction ignores time spent waiting behind other queued frames after the check, and a sudden cost jump (a spike) is only learned through the EWMA, so overshoot is still possible in bursty load. | SPEC 8.4; D44, D45 |

Frames keep the file's own size (`--resolution` is for the synthetic source) and are paced by `--fps`, not the file's frame rate. Looping reopens the file instead of seeking to frame 0 (not reliable for every codec). `--no-loop` (YAML `source.loop: false`) ends the run with `input_eof` (EC-05). `summary.json` records only the input's file name (SR-08 forbids paths outside `--out`); the console still shows the path as given. Tests write their clips with `cv::VideoWriter` (MJPEG in AVI). | SRS FR-SRC-01, FR-SRC-06, VR-14, VR-15, EC-04..EC-06, SR-08; D20 |

## Testing and sanitizers

**Why the tsan preset runs tests under `setarch -R`.** GCC 13's TSan runtime crashes at
startup on recent kernels with high ASLR entropy (`vm.mmap_rnd_bits`); even an empty `main()`
segfaults. The tsan preset sets `CMAKE_CROSSCOMPILING_EMULATOR` to `setarch;-R`, so ctest and
`gtest_discover_tests` run test binaries with ASLR disabled for that process only. No system
setting is changed. Alternatives: `sudo sysctl vm.mmap_rnd_bits=28` (machine-wide), or a
newer toolchain whose TSan runtime handles the higher entropy.

**Why `tsan.supp` suppresses only libtbb.** OpenCV uses TBB as its parallel backend. TBB is
not built with TSan, so TSan cannot see its internal synchronization and reports false races
inside it (seen in the OpenCV `GaussianBlur` smoke test). `called_from_lib:libtbb.so` ignores
only calls made from inside TBB. Nothing in FrameFlow code is suppressed. Cost: a real race
whose accesses happen inside TBB (e.g. freeing a `cv::Mat` while OpenCV still reads it on a
pool thread) would also be hidden, so ASan runs and clear frame ownership still matter.

**Deliberate-race check.** A temporary test had two `std::thread`s increment a plain `int`
captured by reference. The tsan preset reported `ThreadSanitizer: data race` with both stacks
at the `++counter` line, and `halt_on_error=1` made the test fail. After the test was removed
the suite passed again. This proved that races in our own code are still detected with
`tsan.supp` loaded, and that a race fails CI instead of only printing a warning. The test was
not kept.

**Limitation: TSan only sees executed paths.** It checks the happens-before order of accesses
that actually run, so it does not depend on lucky timing, but a race on a path no test
executes (e.g. shutdown while the queue is full, pop timeout) is invisible. Concurrency tests
must therefore exercise shutdown, timeout and overload paths, not just the happy path.
